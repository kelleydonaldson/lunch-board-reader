## How this mirrors the live intake queue

The live queue (worker/_worker.js, "Merchant intake demo") stores two record
kinds in a KV namespace bound as INTAKE. This demo copy keeps the same record
shapes as flat JSON files standing in for the KV entries:

| Live (KV) | Demo copy (here) | Shape |
|---|---|---|
| `evt:<id>` entries + `evt:index` | `store/events.json` + `store/evt_index.json` | `{id, ts, page_id, field, item, verb, post_id, excerpt}` — exactly the fields the live webhook handler writes |
| `draft:<id>` entries + `draft:index` | `store/drafts.json` + `store/draft_index.json` | `{id, event_id, kind, note, ts, status: "awaiting merchant text approval"}` — exactly the fields the live draft handler writes |
| (no live equivalent yet) | `store/flag_pile.json` | Reader reads that fail guardrails or carry flags: `{id, event_id, ts, flags, stops, truck}` — `flags` holds human-readable lines rendered from the model's coded flag objects (brief §5) plus any guardrail problem strings. Gains `approved_stop_indexes` when a reviewer approves individual stops out of the item (see "Per-stop approval" below) |
| (demo board only) | `store/board_entries.json` | Single stops a reviewer individually approved out of the flag pile: `{id, event_id, kind, truck, stop, provenance}` — the board renders these beside the approved drafts' stops. Created only by the explicit `--approve-stop` action |

Demo-only extensions, clearly marked:
- Demo events add `image` (the schedule picture, in `store/images/`) and
  `posted` (the post's date — the weekday anchor). The live queue is text-only
  today; picture + post date beside the text is the approved Reader plan.
- Demo drafts add a `reader` object holding the structured stops, so the demo
  page can show the read beside the post. Live-shaped fields are unchanged.
- Demo drafts carry an approval flow that mirrors production: `status` starts
  at the live value "awaiting merchant text approval", and the demo approval
  step (`reader.py --approve <event_id>`) flips it to "approved" and stamps
  `approved_ts` (demo-only field). Only approved drafts render on the demo
  board — in production, nothing reaches the board without the
  merchant/owner yes either.
- Flag-pile items carry a per-stop review flow (owner addition, brief §3.3):
  `approved_stop_indexes` on the item records which returned stops a reviewer
  has approved; each approval also writes a single-stop entry to
  `store/board_entries.json` with full provenance. The item itself stays in
  the flag pile with its flags intact. Nothing — draft or single stop — is
  ever approved automatically; filing creates zero approvals.
- `page_id` is the literal placeholder `demo-page`; no real page or merchant
  identifiers appear anywhere in this folder.

```
                                        # (repeatable); approved drafts render
                                        # on board.html
python3 reader.py --approve-stop <event_id> <stop_index>
                                        # per-stop approval out of the flag
                                        # pile (repeatable); the one stop
                                        # renders on board.html, the item
                                        # stays in the flag pile
python3 reader.py --approve-stop <event_id> <stop_index> --resolve-date 2026-11-02
                                        # required form when the stop's date
                                        # is null (e.g. case 8 WEEK_UNCLEAR):
                                        # the reviewer supplies the date;
                                        # --resolve-place does the same for a

                                        # the approval refuses, changing nothing

python3 ../../score.py out/extractions.json   # score the filed extractions (all 8)
```

## Per-stop approval from the flag pile (owner addition, brief §3.3)

A flagged post is not all-or-nothing. The reviewer can put ONE returned
stop of a flagged post on the board while the rest of the post stays in
the flag pile — e.g. case 7: the public Sample Public Library stop goes
on the board; the employees-only stop was never returned as a stop (it
exists only as the `PRIVATE_STOP` flag), so it has no approval path at
all. Every approval is an explicit reviewer action
(`reader.py --approve-stop <event_id> <stop_index>`); filing — stub,
simulate, or real — never approves anything.

Rules, all enforced in `approve_stop()` in reader.py (the only per-stop
approval path):

- **Only returned stops can be approved.** Indexes run over the read's
  `stops` array. Flags with `stop: null` (`PRIVATE_STOP`,
  `FLYER_NOT_CONFIRMED`) are not stops — passing `null` as the index
  refuses, and an out-of-range index refuses. Both change nothing.
- **Resolution rule.** A stop whose `date` or `place` is null cannot be
  approved bare. The reviewer must supply the missing value
  (`--resolve-date YYYY-MM-DD` — how a human resolves case 8's
  `WEEK_UNCLEAR` by picking the week — or `--resolve-place "<place>"`).
  Approving without the resolution refuses with a clear error and
  changes nothing; the filed read itself is never edited — it keeps its
  null. The supplied value lands only on the board entry, recorded as
  human-supplied.
- **No double approval.** Approving the same stop twice refuses.
- **The parent item stays.** It keeps its flags and gains
  `approved_stop_indexes` (the 0-based indexes approved so far); the
  queue card shows each stop as "approved → on board" or
  "awaiting reviewer".

Each approval writes one entry to `store/board_entries.json`:

- `id`, `event_id`, `kind`, `truck`, and `stop` — the stop as read, with
  any reviewer resolution applied.
- `provenance.source` — `"flag_pile"`.
- `provenance.source_event_id` — the flag-pile item's event id.
- `provenance.source_flag_entry_id` — the flag-pile entry's own id.
- `provenance.stop_index` — the 0-based index of the approved stop.
- `provenance.approved_ts` — when the approval happened.
- `provenance.approval` — states the approval was a reviewer action via
  the explicit `--approve-stop` command; nothing approves automatically.
- `provenance.human_supplied` — `{}` when the read was complete, else
  the reviewer-supplied values, e.g. `{"date": "2026-11-02"}`.

## Stand-in mode vs real mode

There is exactly one seam between the two modes: **`call_model_api()` in
reader.py** — the single function that turns (image, recipe prompt) into a
structured extraction.

- **Stand-in mode (today).** `call_model_api` is never invoked.
  `--simulate` feeds ready-made extractions through the identical
  guardrails + filing path the real reads will use. The Step 5 early build
  fed the kit's answer key in as the stand-in reads, so the staged store,
  queue and board hold exactly what perfect model reads would produce:
  8 events, 4 drafts (cases 1, 2, 3, 6 — all approved in the demo), and
  4 flag-pile entries (case 4 `UNREADABLE`, case 5 `NO_STREET_ADDRESS`,
  case 7 `PRIVATE_STOP`, case 8 `WEEK_UNCLEAR`). One per-stop approval
  has since been applied as an explicit reviewer action: case 7's stop 0
  (Sample Public Library) is in `store/board_entries.json` and on the
  board (10 stops total); the stops of cases 4, 5, and 8 remain
  unapproved in the flag pile.
- **Real mode (when the credits land).** Implement ONLY the body of
  `call_model_api`: call the connector helper
  (`~/workspace/custom-connectors/custom.meta-model-api/bin/meta_model_api.py
  vision --image <path> --prompt <prompt> --model muse-spark-1.3`) and
  parse its reply into the §5 schema. The recipe, guardrails, filing,
  approval step, queue and board do not change. First real run per
  Kelley's instruction: case 1 alone, raw response + score shown to him,
  then the rest.
